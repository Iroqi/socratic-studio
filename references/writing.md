# Interactive HTML 写稿参考

> 制品的写作层负责“写什么、怎么讲”，**不负责套模板**。知识边界来自 Learning Graph
> （`graph-schema.md`），页面结构与呈现方式由 Agent 依据内容自由决定。
> **讲解顺序：** Lesson IR 的 `steps[]`（形状与字段见 `lesson-ir.md`）是**默认讲解顺序**
> （已按 `depends_on` 拓扑排序）。当内容的认知路径明确更优时可局部调整，但调整**不得违反
> `depends_on`**，且需在对话中向学习者说明调整意图。

## 1. 从认知路径出发

写 HTML 之前先想清楚这一份讲解要带读者走的路：

- 从哪个**问题或困惑**切入？
- 中间有哪几个**转折**（一次比较、一次预测、一次操作）？
- 结尾要带走什么**可复述的结论**？

页面结构是这条路径的影子。不要先选一个骨架再往里填内容。

## 2. 内容层语义

组织内容时优先保留这些来源信息。**两组来源不要混**——它们分属两份不同的输入：

**来自 Learning Graph / Lesson IR（知识侧）：**

- `concept_id`：来源知识概念。
- `title` / `summary` / `explanation`：可读标题与讲解内容。
- `examples` / `misconceptions` / `assessment_items`：教学证据（字段定义见 `lesson-ir.md`）。

**来自旁白脚本（听觉侧，`narration.py --source` 的输入，不是 IR 字段）：**

- `text`：精炼口播稿；用于 TTS。
- `body`：供阅读的更完整正文，可比口播更丰富。
- `tagline`：可选上下文标签。

（旁白脚本的完整形状见 `media.md`「音频（TTS）」；`lesson-ir.md` 明确"旁白不走 Lesson IR"。）

**视觉表达**不属于任何一组数据源：它是你声明**语义角色**（流程、因果、结构、比较、数据、
动态过程）的方式，不指定固定图片槽。

## 3. 旁白稿（Narration）

`text` 应优先写成**自然口语**：一句只承载一个主要认知动作，关键处允许短停顿。旁白脚本交
`narration.py` 生成音频与时间轴（用法见 `media.md`「音频（TTS）」）。

- TTS 只在需要配音时才用；没有配音，页面必须照样成立。
- 旁白不决定页面结构——它只是内容的**听觉通道**。

## 4. Learning-first 写作原则

**分层适用。** 这一节里有一条对**所有**制品无条件的底线，其余是可随制品尺寸放宽的推荐项。
不要因为"制品很小、很临时"就连底线一起放弃；也不要拿成品的完整标准去卡一个 40 行的即时模拟器。

**底线（无条件）：**

- 制品必须在**没有音频、没有自动播放、没有引导播放**的情况下仍然成立。正文不要依赖
  “下一帧才出现”的上下文。
- 不能出现**只有作者知道怎么用**的交互：任何可点/可拖/可输入的东西，页面上要有一句
  说明它是什么、点完会发生什么。
- 不能把**唯一的信息**放在动画里。动画只能是已有信息的增强，不是它的唯一载体。

> 底线不随尺寸变化。一个 30 行的模拟器也必须满足这三条——否则它在别人那里就是坏页面。

**推荐（按尺寸取舍）：**

- 让核心信息本身可滚动阅读。
- 让图、文字、交互自然进入内容流。
- 将动画作为注意力增强，而不是内容载体。
- 将 check/choice 用于认知转折，不要把所有交互退化成结尾测验。
- 交互要有**真实用途**：预测、判断、比较、操作、反思、练习。没有 authored assessment 就不硬加选择题。

> 推荐项在**小尺寸交互物件**上可放宽：如果这一段的目的是"亲手拖一下感受弹簧阻尼"，
> 那它的价值就在那个手感里，不必再配可滚动的完整讲义。判断依据是**这段教学的认知动作**
> 需要什么——需要读的东西写得能读，需要玩的交互做得能玩，不要两边都只做一半。

### 4.1 交互深度分级（按概念类型选，不要一律停在第一级）

| 深度 | 学习者在做什么 | 适合的概念 |
|---|---|---|
| 调参试错 | 改一个值，看结果怎么变 | 有可操作机制的概念（参数、阈值、边界） |
| 预测验证 | 先猜，再公布真实结果 | 有明确因果、能产生预期偏差的概念 |
| **建构** | 自己搭出结构 / 排定顺序 | 结构性、系统性知识 |
| **设计** | 自己定目标与约束，做完自评 | 技能类、项目类内容 |

**「项目化」的本质就是把交互推到后两级。** 边界不变：即使是项目 / 游戏形态，教学仍在对话里推进。

**深度 ≠ 炫技。** 这张表量的是**学习者在做什么**（调参 / 预测 / 建构 / 设计），不是**效果多花哨**。
下面这些东西**不算深度**，只是在挤占注意力，默认不要：

- 不承载任何信息的入场动画、粒子、光效
- 为了"高级感"加的缩放 / 悬浮特效 / 3D / Dashboard 外壳
- 同一份信息的第二张、第三张重复图
- 纯装饰的分隔、图标、渐变

判据还是那一条：**这段的认知动作需要什么**。需要动手就让人动手（深），不需要就老实静态——
**"多给点交互"和"多给点动画"都不是默认值。** 生成后的自查见 `media.md`「生成后的快速自查」。

## 5. 视觉表达

需要视觉时**先说明语义角色**：流程、因果、结构、比较、数据、真实参考、动态过程等。
先定语义，再选实现——**「语义角色 → 首选实现」的对应表见 `media.md`「按语义选实现」**，
本文不复制（同一张表存两份必然漂移）。

写作侧只需要守住一条：视觉不应绑定固定尺寸或固定布局槽；最终呈现由内容需要决定。

**本节只立判据。** 判据说"该有"，接下来"**怎么画得让人一眼看懂**"见 `media.md`「让人看懂」
（六个动作）、非时间轴的图怎么组织见 `media.md`「静态视觉的实现骨架」、画完看着不对怎么查见
`media.md`「画面做出来了但不对」。

### 5.0 视觉与数据（canonical：禁令与正向要求成对）

**本节是「视觉与数据」这条纪律的 canonical home。** 一句话：

> **数据不存在就别画；数据存在就必须用起来。** 两端都是硬要求，只做其中一端都不合格。

这条纪律有两个方向，成对成立、缺一不可：

**方向一 · 禁令（防伪造）：视觉只在有真实语义数据时生成，没有就老实用文字。**
没有 `depends_on` 就不画依赖图，没有可信数值就不画坐标图——**画了不存在的东西就是编造，
比不画更糟**。画出来之后必须真（不编造数据、不用误导性比例、不把估算当事实、不凭空造关系）
的具体标准，见 `media.md`「不许编造」；那一节管"画出来的真不真"，本节管"该不该画"。

**方向二 · 正向要求（防偷懒）：Learning Graph 里已有的数据，必须出现在制品上。**
只有禁令时，保守的执行者会整体退回纯文字，因为纯文字永远不违反禁令。所以补三条正向判据：
命中下表任一条，**没有**对应视觉就是不合格——

| 概念具有什么 | 制品上必须有什么 | 数据来源（都在 Learning Graph 里） |
|---|---|---|
| 概念之间**存在关系**（依赖 / 包含 / 对立） | 结构图（概念图：节点 + 有向边） | `depends_on`、`confused_with` |
| 概念有**空间 / 几何 / 数量**含义 | 图形——不是列表，不是文字描述 | `examples` |
| 概念有**过程**（见 §5.1） | 动态呈现 | — |

**关键：这些数据源早就躺在 Learning Graph 里了**，只是从来没有一条规则要求它们出现在制品上。
所以这一条**不增加任何新能力**，只要求把已经有的数据用起来。两端合起来才完整：
先确认数据真实存在（方向一），存在就据它画出视觉（方向二）。

### 5.1 什么时候**必须**有动态呈现（正向要求）

上面的底线只说「不要怎样」，不够——**只列禁令，执行者会整体退回静态文字**，
产出「有声课件」这一本 skill 明确反对的形态（特征清单见 §5.2）。

**判据：如果这一段的认知动作本身是「随时间变化的」，就必须有动态呈现。**

> **这条不是"默认加动画"。默认仍然是静态。** 只有命中下面四条判据之一（或 §5.0 三条正向判据之一）
> 时，"动"才是**义务**；不在判据里的段落就老实静态，不要顺手给它配入场动画、位移或渐显——
> 那是另一种偷懒：用**没有信息量的动效**冒充"做了设计"（`media.md`「生成后的快速自查」有对应的
> 自查项）。
> **「该动的地方不许用静态糊过去」与「不该动的地方不许炫技」是同一条纪律的两面。**

满足以下任一条，静态呈现就是不合格的：

| 情形 | 静态做法（不合格） | 应有做法 |
|---|---|---|
| 过程有**先后顺序**且顺序本身是信息 | 把过程一次性铺成表格/列表 | 按时间轴逐步演进（元素逐个出现/位移/变色） |
| 有**比较**且比较是逐位的 | 直接给出结论「1 < 10」 | 让两个对象对齐、逐位亮起、在分歧处分开 |
| 有**状态变化**（排序中、指针移动、变量改写） | 只给初始值与最终值 | 展示中间态，让学习者看到"正在发生" |
| 有**因果链** | 并列写出原因与结果 | 让因先发生、果跟着出现，视觉上连起来 |

**配了旁白时，时间轴就是动画的时钟。** 旁白脚本已经产出了逐句起止时间
（`narration_timing.json`），**不要只拿它高亮段落**——让画面随旁白演进：念到哪个子句，
对应的视觉元素就出现/变化。旁白与画面是**同一份内容的两个通道**，不是音轨+字幕。

**具体骨架与 SVG 实现坑**（预置舞台 + 渲染器 = f(句索引)、CSS transform 覆盖 SVG 属性的
静默失败、两拍位移）见 `media.md`「时间轴驱动与画面演进（配了旁白时）」——本节只立判据，不复制实现细节。

> **与底线的边界（重要）：** 「不能把唯一信息放在动画里」仍然成立。做法是让**动画承载
> 过程**、**文字承载结论**——学习者跳过动画也能读到结论，但看完动画才真正"看见"过程。
> 两者合起来才完整；不是把结论也塞进动画，也不是用静态文字替代动画。

### 5.2 反模式：有声课件

以下特征出现两条以上，基本可以断定做成了课件，应重做：

- 页面主体是「若干 `<section>`，每节一段说明 + 一个静态代码块/表格」
- 旁白内容与正文文字**高度重合**（念的和读的是同一句）
- 动画/过渡只用于**入场**（fade-in），不承载任何过程信息
- 时间轴数据只用来做高亮/滚动定位
- 所有交互集中在结尾（"学完了，来测测"），中途没有可操作/可观察的东西

### 5.2.1 答完之后：时序引导规范见 interactive-runtime.md

学习者答对一题之后，页面必须回答"我现在该做什么"——这是最容易漏的一环。
**但"怎么给这条继续路径"是播放器 / 门禁的交互规范，不是写作规范**：自动续播、显式
"继续 →"按钮、未作答时的提示、冻结期播放控制说明、键盘空格语义、继续按钮与门禁完成信号
（`MutationObserver`）的接线，其 canonical 全部在 `interactive-runtime.md`——
见「答后交互与播放控制（宿主页规范）」整节（完成信号接线细节另见「门禁完成信号（MutationObserver）」），本节只要求你在写作时
**为答后反馈留出一句话的位置**（说清"选对即可继续"与"下一题大约在哪"）。

## 6. 对话

多人对话可以通过说话人区分（如 `speakers` 概念）表达。不同说话人的音色只影响 TTS，不改变页面结构。
