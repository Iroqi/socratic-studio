# 制品写作与交互协议

> **何时读取:** 写制品时读。要用交互式选项、题型、学习看板、动态 HTML 或宿主回传事件时，读 §6 之后；
> 简单文字解释不需要。
>
> 写作层负责“写什么、怎么讲”，**不负责套模板**。UI 是 Graph 和 Progress State 的投影，不是新知识源，
> 也不是独立的学习模式。知识边界来自 Learning Graph，页面结构与呈现方式由 Agent 依据内容自由决定。
> **讲解顺序：** `graph_compiler.py` 输出的 Graph 已按 `depends_on` 拓扑排序，其 `concepts[]` 顺序是默认
> 顺序；认知路径明确更优时可局部调整，但**不得违反 `depends_on`**，且需向学习者说明调整意图。

## 1. 从认知路径出发

写 HTML 之前先想清楚这一份讲解要带读者走的路：

- 从哪个**问题或困惑**切入？
- 中间有哪几个**转折**（一次比较、一次预测、一次操作）？
- 结尾要带走什么**可复述的结论**？

页面结构是这条路径的影子。不要先选一个骨架再往里填内容。

## 2. 内容层语义

组织内容时优先保留这些来源信息，**两组来源不要混**：

- **知识侧**（Learning Graph）：`id`、`name` / `summary` / `explanation`、
  `examples` / `misconceptions` / `assessment_items`。
- **听觉侧**（旁白脚本，`narration.py --source` 的输入，独立于 Graph）：`text` 精炼口播稿。
  完整形状见 `media.md`「音频（TTS）」。

**视觉表达**不属于任何一组数据源：它是你声明**语义角色**（流程、因果、结构、比较、数据、动态过程）
的方式，不指定固定图片槽。

## 3. 旁白稿（Narration）

`text` 应优先写成**自然口语**：一句只承载一个主要认知动作，关键处允许短停顿。旁白脚本交
`narration.py` 生成音频与时间轴（用法见 `media.md`「音频（TTS）」）。

- TTS 只在需要配音时才用；没有配音，页面必须照样成立。
- 旁白不决定页面结构——它只是内容的**听觉通道**。

## 4. Learning-first 写作原则

**分层适用。** 这一节里有一条对**所有**制品无条件的底线，其余是可随制品尺寸放宽的推荐项。
不要因为"制品很小、很临时"就连底线一起放弃；也不要拿成品的完整标准去卡一个 40 行的即时模拟器。

**底线（无条件）：**

- 制品必须在**没有音频、没有自动播放、没有引导播放**的情况下仍然成立。正文不要依赖
  “下一帧才出现”的上下文。
- 不能出现**只有作者知道怎么用**的交互：任何可点/可拖/可输入的东西，页面上要有一句
  说明它是什么、点完会发生什么。
- 不能把**唯一的信息**放在动画里。动画只能是已有信息的增强，不是它的唯一载体。

> 底线不随尺寸变化。一个 30 行的模拟器也必须满足这三条——否则它在别人那里就是坏页面。

**推荐（按尺寸取舍）：**

- 让核心信息本身可滚动阅读。
- 让图、文字、交互自然进入内容流。
- 将动画作为注意力增强，而不是内容载体。
- 将 self_check/predict/choice 用于认知转折，不要把所有交互退化成结尾测验。
- 交互要有**真实用途**：预测、判断、比较、操作、反思、练习。没有 authored assessment 就不硬加选择题。

> 推荐项在**小尺寸交互物件**上可放宽：如果这一段的目的是"亲手拖一下感受弹簧阻尼"，
> 那它的价值就在那个手感里，不必再配可滚动的完整讲义。判断依据是**这段教学的认知动作**
> 需要什么——需要读的东西写得能读，需要玩的交互做得能玩，不要两边都只做一半。

### 4.1 交互深度分级（按概念类型选，不要一律停在第一级）

| 深度 | 学习者在做什么 | 适合的概念 |
|---|---|---|
| 调参试错 | 改一个值，看结果怎么变 | 有可操作机制的概念（参数、阈值、边界） |
| 预测验证 | 先猜，再公布真实结果 | 有明确因果、能产生预期偏差的概念 |
| **建构** | 自己搭出结构 / 排定顺序 | 结构性、系统性知识 |
| **设计** | 自己定目标与约束，做完自评 | 技能类、项目类内容 |

**「项目化」的本质就是把交互推到后两级。**

**深度 ≠ 炫技。** 这张表量的是**学习者在做什么**（调参 / 预测 / 建构 / 设计），不是**效果多花哨**。
下面这些东西**不算深度**，只是在挤占注意力，默认不要：

- 不承载任何信息的入场动画、粒子、光效
- 为了"高级感"加的缩放 / 悬浮特效 / 3D / Dashboard 外壳
- 同一份信息的第二张、第三张重复图
- 纯装饰的分隔、图标、渐变

判据还是那一条：**这段的认知动作需要什么**。需要动手就让人动手（深），不需要就老实静态——
**"多给点交互"和"多给点动画"都不是默认值。**

## 5. 视觉表达

需要视觉时**先说明语义角色**（流程、因果、结构、比较、数据、真实参考、动态过程），再选实现——
「语义角色 → 首选实现」的对应表在 `media.md`「按语义选实现」。写作侧只守一条：视觉不绑定固定尺寸或
固定布局槽，呈现由内容需要决定。

**本节只立判据。** 判据说"该有"；怎么画得让人一眼看懂、静态图怎么组织、画完看着不对怎么查，
是 `media.md`「让人看懂」「静态视觉的实现骨架」「画面做出来了但不对」三节的事。

### 5.0 视觉与数据：禁令与正向要求成对

> **数据不存在就别画；数据存在就必须用起来。** 两端都是硬要求，只做其中一端都不合格。

这条纪律有两个方向，成对成立、缺一不可：

**方向一 · 禁令（防伪造）：视觉只在有真实语义数据时生成，没有就老实用文字。**
没有 `depends_on` 就不画依赖图，没有可信数值就不画坐标图——**画了不存在的东西就是编造，比不画更糟**。
"画出来的必须真"的具体标准见 `media.md`「不许编造」：那节管真不真，本节管该不该画。

**方向二 · 正向要求（防偷懒）：Learning Graph 里已有的数据，必须出现在制品上。**
只有禁令时，保守的执行者会整体退回纯文字，因为纯文字永远不违反禁令。所以补三条正向判据：
命中下表任一条，**没有**对应视觉就是不合格——

| 概念具有什么 | 制品上必须有什么 | 数据来源（都在 Learning Graph 里） |
|---|---|---|
| 概念之间**存在关系**（依赖 / 包含 / 对立） | 结构图（概念图：节点 + 有向边） | `depends_on`、`confused_with` |
| 概念有**空间 / 几何 / 数量**含义 | 图形——不是列表，不是文字描述 | `examples` |
| 概念有**过程**（见 §5.1） | 动态呈现 | — |

**这一条不增加任何新能力**，只要求把已经有的数据用起来：先确认数据真实存在（方向一），
存在就据它画出视觉（方向二）。

### 5.1 什么时候**必须**有动态呈现（正向要求）

上面的底线只说「不要怎样」不够——**只列禁令，执行者会整体退回静态文字**，产出一本 skill 明确反对的
「有声课件」（特征清单见 §5.2）。

**判据：如果这一段的认知动作本身是「随时间变化的」，就必须有动态呈现。**

> **这条不是"默认加动画"。默认仍然是静态。** 只有命中下面四条判据之一（或 §5.0 三条正向判据之一）
> 时，"动"才是**义务**；不在判据里的段落就老实静态，不要顺手给它配入场动画、位移或渐显——
> 那是另一种偷懒：用**没有信息量的动效**冒充"做了设计"（`media.md`「生成后的快速自查」有对应的
> 自查项）。
> **「该动的地方不许用静态糊过去」与「不该动的地方不许炫技」是同一条纪律的两面。**

满足以下任一条，静态呈现就是不合格的：

| 情形 | 静态做法（不合格） | 应有做法 |
|---|---|---|
| 过程有**先后顺序**且顺序本身是信息 | 把过程一次性铺成表格/列表 | 按时间轴逐步演进（元素逐个出现/位移/变色） |
| 有**比较**且比较是逐位的 | 直接给出结论「1 < 10」 | 让两个对象对齐、逐位亮起、在分歧处分开 |
| 有**状态变化**（排序中、指针移动、变量改写） | 只给初始值与最终值 | 展示中间态，让学习者看到"正在发生" |
| 有**因果链** | 并列写出原因与结果 | 让因先发生、果跟着出现，视觉上连起来 |

**配了旁白时，时间轴就是动画的时钟**（用法见 `media.md`「时间轴驱动与画面演进」）：旁白与画面是
同一份内容的两个通道，不是音轨+字幕。

**具体骨架与 SVG 实现坑**（预置舞台 + 渲染器 = f(句索引)、CSS transform 覆盖 SVG 属性的
静默失败、两拍位移）见 `media.md`「时间轴驱动与画面演进（配了旁白时）」——本节只立判据，不复制实现细节。

> **与底线的边界（重要）：** 「不能把唯一信息放在动画里」仍然成立。做法是让**动画承载
> 过程**、**文字承载结论**——学习者跳过动画也能读到结论，但看完动画才真正"看见"过程。
> 两者合起来才完整；不是把结论也塞进动画，也不是用静态文字替代动画。

### 5.2 反模式：有声课件

以下特征出现两条以上，基本可以断定做成了课件，应重做：

- 页面主体是「若干 `<section>`，每节一段说明 + 一个静态代码块/表格」
- 旁白内容与正文文字**高度重合**（念的和读的是同一句）
- 动画/过渡只用于**入场**（fade-in），不承载任何过程信息
- 时间轴数据只用来做高亮/滚动定位
- 所有交互集中在结尾（"学完了，来测测"），中途没有可操作/可观察的东西

## 6. 设计定位

采用混合模式:

```text
对话: 理解目标 / 解释 / 追问 / 开放式推理
UI:   选择 / 操作 / 反馈 / 状态展示
状态: Learning Graph + Progress State
```

不要把每条消息都改造成 UI。只有当 UI 能降低选择成本、表达状态变化，或让用户直接操作一个模型时才生成 UI。

**优先级:**

1. 简单解释 → 直接文字
2. 单个离散决定 → 一个紧凑选择组件
3. 动态过程或空间关系 → 一个主视觉 + 最少控制
4. 需要带走、复用或分享 → Agent 直接生成并按需保存 HTML 制品

### 6.1 能力分级与降级

按当前会话可用能力选择最高等级，不把更高等级当作前置依赖:

| 等级 | 能力 | 失败时 |
|---|---|---|
| L0 | Markdown/文字问答 | 始终可用的最终兜底 |
| L1 | 原生 button/input/select/textarea | 用短编号列表或一句一问 |
| L2 | 内联 HTML/SVG/Canvas 视觉 | 用静态 SVG、Mermaid 或文字步骤 |
| L3 | 宿主回传/追问桥接 | UI 只做本地展示，不要求模型立即响应 |
| L4 | 可选的图像、视频或插件能力 | 跳过该增强，缺素材处用一句文字说明，不阻塞主循环 |

**降级规则:** 只为核心学习动作保留文字兜底；可视化、动画、图片和插件失败时不反复重试，不声称已经生成或保存了结果。
**素材类降级的阶梯（换最接近的能力 → 降复杂度 → 保留核心信息 → 如实说明限制）见 `media.md`「能力不可用时的降级」**——
本节只管表现形式的等级，那一节管单一素材能力失败后怎么走。

## 7. 选择呈现形式

| 场景 | 首选 | 不要做 |
|---|---|---|
| 目标澄清 | 2–4 个选项 | 一次询问所有背景信息 |
| 诊断选择 | 单题卡片 | 把多个独立问题塞进一张卡片 |
| 开放推理 | 文字回答 | 用选择题替代解释过程 |
| 过程/状态变化 | 步进视觉或局部动画 | 同时堆多个图和控制条 |
| 主动回顾 | 继续 / 换题 / 回顾 三选一 | 复杂日历和统计面板 |
| 学习进度 | 一张主看板 | 把所有内部字段都展示给学习者 |

一个 UI 表面只服务一个当前决定。不要为了“看起来像产品”添加搜索、筛选、工具栏、装饰卡片或无关指标。

## 8. 题型与证据

题型可以丰富，但题型只是输入形式，不改变 mastery 状态机。所有题型都必须映射到 concept、目标能力和证据类型。

| 题型 | 适合测量 | 证据限制 |
|---|---|---|
| 单选/多选 | 概念辨析、误解定位 | 单次选对不足以证明掌握 |
| 判断 | 快速诊断、反例识别 | 必须避免依赖猜测概率 |
| 排序/匹配 | 顺序、依赖、分类 | 记录具体错位位置 |
| 参数操作/模拟 | 因果关系、状态变化 | 记录操作序列和最终结果 |
| 代码/命令操作 | 应用能力、执行错误 | 有执行环境时以真实结果为准 |
| 开放回答 | 解释、迁移、推理 | 不得被 UI 选择项替代 |

选择题的干扰项应绑定已知 misconception；否则它只能做快速检查，不能被当作高质量 mastery 证据。

## 9. 交互事件协议

每次 UI 操作都应能映射成一个最小事件。事件由宿主/Agent 从对话回答或 DOM 快照写入当前
Runtime 上下文，不由可选运行时库导出，也不直接修改 Learning Graph。

```json
{
  "event_type": "answer_submitted",
  "concept_id": "closures",
  "question_id": "q_12",
  "interaction_type": "choice",
  "response": "B",
  "result": "correct",
  "client_time": "optional"
}
```

**必需字段:** `event_type`、`concept_id`、`question_id`、`interaction_type`、`response`。

**`result`:** `correct` / `incorrect` / `recorded`，仅客观题经 Agent 判定后写入；开放式/主观题省略。
**`client_time`:** 可选，仅作时序参考，不参与状态判定。本节定义字段协议，持久化形态见
`persistence.md`「[EVENTS] 的写法」。

**处理顺序:**

1. 校验事件是否完整、是否属于当前 question。
2. 将事件转换为 Runtime 可读的回答和证据。
3. 由 EVALUATE 判断正确性与错误类型。
4. 由 UPDATE MASTERY 更新 Progress State（各环节职责划分与状态写入权限以 `runtime.md`「环节边界」为准）。
5. 生成下一张 UI 或回到对话解释，不直接让 UI 修改 Graph。

重复提交、过期 question 或无法解析的事件应被忽略并给出可恢复提示，不得污染 mastery 状态。

## 10. 看板与状态投影

看板是只读投影，至少包含:

- 当前 concept 和学习目标
- 学习阶段的自然语言描述
- 待处理的一个动作
- 已观察到的证据摘要
- 下一步建议

不要默认展示 `state`、诊断维度、PATCH 或状态机术语。用户主动要求调试细节时才展示内部视图。

看板更新来源只能是 Progress State 和已确认的事件；不能在 UI 中另存一套 mastery 分数，也不能让用户直接拖动进度条改变掌握状态。

## 11. 动态更新循环

"实时"= 事件级更新（§9 的协议就是循环本身：操作 → 事件 → 评估 → 局部重渲染），不要求模型持续向
HTML 推送 token。宿主回传能力不可用时，保持 UI 的本地展示并在正文继续提问；不要让学习 UI 依赖未确认
的网络、WebSocket、后端 API、鉴权或持久化职责——需要真正的服务端数据时，先由外部工具或后端取得，
再把结果作为输入交给 Runtime。

### 11.1 DOM 观测映射

运行时不导出遥测，证据由 Agent/宿主从页面读出来。可观测交互标注 `data-concept-id` 与
`data-question-id`；作答状态标记（`data-completed` / `data-locked` / `data-result` / `data-response` /
`data-attempts`）由宿主页维护，引入可选运行时库时由它代写（取值与写入时机见
`interactive-runtime.md`「门禁完成信号（MutationObserver）」）。
这些属性只是 DOM 快照，不是第二套 Progress State；消费侧仍需校验当前题目、去重过期操作，再交给
EVALUATE / UPDATE MASTERY。序列化成 `[EVENTS]` 行时的字段对应：`data-concept-id` → `concept_id`、
`data-question-id` → `question_id`、`data-interaction-type` → `interaction_type`、
`data-response` → `response`、`data-result` → `result`。

## 12. 外部能力与插件

图片、视频和其他 skill/plugin 都是增强项。调用前确认:

- 当前会话确实提供该能力
- 该能力对当前 concept 有教学价值
- 输出能回到当前 concept 或当前学习目标
- 失败后仍有文字或静态视觉方案

插件输出要记录来源和用途，但不要把插件名暴露成学习流程中的必经步骤。一次只调用最有价值的增强能力，避免把学习主线变成工具编排。
