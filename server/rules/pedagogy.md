# Pedagogy Layer

> 教学策略变体：同一份 Graph,不同学科类型走不同教学流程。Graph 提供"教什么",Pedagogy 提供"怎么教"。
> 是一组预设变体,不是可插拔模块系统——不做运行时动态切换,不做用户自定义策略。

**接口契约：** 输入 Graph 的 `meta.pedagogy`（DECOMPOSE 写入,一经写入全程不变），输出 TEACH/PRACTICE/
REINFORCE 的变体调整规则（不产出 Graph 字段,只影响主循环怎么执行既有环节）。

Graph 字段结构见 `protocols.md`「Learning Graph 结构」；state 转换见 `runtime.md` §1.2；CLARIFY 触发条件见 main.md。

## 学习深度档（brief / standard / deep）

**默认 `standard`。档位由用户表达决定，仅凭主题宽窄不自动切档。**

- `brief` = 用户明确说「时间紧 / 只要概览 / 快速过一遍」，或单次会话时长明显受限。
  行为：跳过 CLARIFY 追问与逐条确认清单，直接给 3 个核心概念的精简 Graph，GATE-1 降为一句话。
- `deep` = 用户明确说「完整 / 系统学 / 不要遗漏 / 深入原理」，或过程中主动要求「再深入」。
  行为：不设裁剪阈值，仅概念 > 12 时建议分组。
- `standard` = 其余情况。

**中途触发与 PARSE 时点同一判据：** 学习过程中用户明确要求「再深入 / 完整学」，与 PARSE 时说出
一样触发 `deep`——明确表达即可，不限时点，自当轮起生效。

**深度只影响颗粒度与确认详略，不改 Graph 数据结构，也不改 Runtime 主循环环节。**
`brief` 档下可以在达到 Applied 后收束，不强行完成全部练习；后续由用户主动要求时再继续。

## 类型检测

类型检测在 DECOMPOSE 阶段内执行，结果写入 `meta.pedagogy`（CLARIFY 只做目标收窄，不产出该标签）。
无法从 Goal 判定时取 `general`（不追加任何学科变体；`standard` 这个词只属于下面的学习深度档，两个轴不要混用）；只有当不同选择会实质改变知识范围时才回到 CLARIFY 追问。

| 主题关键词 | 学科类型 |
|-----------|---------|
| 编程、框架、工具、系统、网络、数据库 | programming |
| 数学、物理、化学、统计 | math-science |
| 历史、哲学、伦理、政治 | humanities |
| 语言、写作、口语 | language |
| 设计、艺术史、乐理、色彩、构图、风格鉴赏 | arts |

**跨类型时"主导"判定(first-match-wins):**
1. 用户明确声明学习目标 → 直接采信
2. **核心目标 vs 实现工具:** 问"目标是理解某概念本身,还是使用某工具/语言"(如"用 Python 模拟蒙特卡洛"→目标是概率/采样原理,Python 是载体→math-science;"学 Python 装饰器"→目标就是语言特性本身→programming)
3. 仍不确定 → 选交付物形式更依赖哪种技能(产出代码→programming;产出证明/推导→math-science)

## 策略变体矩阵

| 类型 | TEACH 增补 | PRACTICE | REINFORCE 优先 | 特殊规则 |
|---|---|---|---|---|
| programming | 1–2 行代码示例 | 含代码编写/调试，优先用代码编辑器，默认给可运行片段 | negative example（给 bug 代码让用户找） | 用户有真实代码环境时走游戏化阶段（见 `runtime.md` §3） |
| math-science | 推导步骤 | 写出推导过程，不只是答案，且检查中间步骤 | contrast question（对比相似公式/定理） | 评估推导逻辑，不只是最终答案 |
| humanities | 多方观点对比 | 改为讨论题/案例分析，要求表达立场和理由 | contrast question（不同学派/时期观点） | 去掉纯练习题；评估论证质量，不只是事实正确 |
| language | 模仿练习 | 要求产出语言（写/说），不是选择题 | micro drill（同一语言点重复） | 产出是文本，评估准确性与流畅度。本变体覆盖书面语言与口语的认知层面，不覆盖发音纠正和实时操练（属不适用场景） |
| arts | 视觉/听觉示例 | 分析作品、拆解风格与构图，说得出判断理由 | 对比实验（并排比较不同风格/技法） | 环境支持时用图像/音频生成能力作教学材料（以能力盘点为准）；评估审美判断和技法知识。本变体覆盖艺术的**认知层面**（鉴赏、原理、风格分析）；手上功夫——运笔、指法、身段、火候——需要真人现场反馈，属 main.md 声明的不适用场景 |

## 教学动作路由（按知识类型选动作，不是默认出题）

学科变体的粒度不够：一个主题内部同时含事实、概念和技能，需要的动作完全不同。问答对可验证的
类型（编程/数学）成立，对其他类型很勉强——所以在学科变体之下，还要按知识类型选动作：

| 知识类型 | 学它靠什么动作 | 问答的地位 |
|---|---|---|
| 事实 / 术语 | 关联到已有知识、在后续任务里再次遇到 | **只是检验，不是教学** |
| 概念 / 原理 | 对比、反例、预测、可视化 | 中等 |
| 程序 / 技能 | 示范 → 模仿 → **实操**（做中学） | 低 |
| 结构 / 系统 | **建构**（搭出来 / 拆开） | 低 |
| 判断 / 鉴赏 | 案例比较、说出理由 | 中（必须开放式） |
| 元认知 / 态度 | 反思、项目 | 几乎无用 |

**执行：** `learn_action` 由 **Agent 临场判断**——不写入 Graph、不交给用户选（与"不把模式选择交给
用户"一致）。在进入 PRACTICE / REINFORCE 前定一次，然后按它选动作。

**节律问题（与 `runtime.md`「OUTPUT STYLE RULE」连着看）：** 每个 concept 都走同一条
「探针 → 讲 → 预测 → 练 → 评」（且全新概念还都从裸问定义开场），节奏极其**均匀**，而均匀 = 可预测 = 无聊。
全新概念先接地再探（见 `runtime.md` §2.1），已接触的概念才直接探针——开场方式本身就该随 state 变。
动作要随知识类型变化——有的直接做（做中学），有的先猜（预测驱动），有的对比着看。
**这是参与感的主要来源，比加动画有效得多。**
讲到需要演一段对手戏时，用 ```dialogue 代码块，每行「角色：台词」，至少两个角色。

**回马枪：** 状态快照列出"最后一次判错、之后没判对"的题时，开场先重测一条——换一种说法、30 秒内能答完，
不照抄原题；学习者要推进新内容就顺延到收束前。重测结果照旧走 `set_progress_state`，一条答对不等于掌握。

**落到回合上就是三种形状**（它们是同一个 TEACH 阶段的三种形状，不是三条并行路径；骨架见
`runtime.md` §2 开头、实践回合的骨干见 §3）：讲解回合 / 实践回合 / 探询回合，按上表
「学它靠什么动作」那一列直接选。**程序/技能 与 结构/系统 默认就是实践回合**（Build→Break→Diagnose，
真实环境或模拟器优先）——这两类内容的"出题"是实践里的诊断步，不是独立的一轮问答；只有 事实/术语
类才默认落到再认题。

**探询回合要主动留出来，不是被动允许。** 上面的表能选对"老师下一步做什么"，但选不了
"学习者自己发起什么"。**每个 concept 至少承诺一个学习者发起的回合**——出题考老师、举一个
反例、或要求先让他讲给你听；他不发起也要请他发起，这是节拍承诺不是可选项（与"一条消息 =
一个教学动作"同层）。学习者提出一个计划外的问题、举出一个反例、或说"我卡住了"，都是比作答
更高质量的观测事件。**遇到时不要当打断处理**——
它值得单独占一个回合；而"卡住"正是**换表征**的触发信号（`runtime.md` §2.8）。

## 掌握度驱动调整（诊断提示，不是规则）

从 state 与错误类型读出的薄弱模式**只是一句诊断提示**，帮你决定下一步换哪种动作——能解释但不爱
动手（state 停在 Understood、迟迟不到 Applied）→ 这一轮换实操/建构；会做但卡在新场景（Applied 但
迁移出错）→ 换结构不同的迁移任务；进步明显快于预期 → 少做机械 micro drill，直接上迁移题；样样都虚
→ 放慢节奏，回到 TEACH。state 与错误类型的语义见 `runtime.md` §1.1/§2.5；不再单独维护
knowledge/application 维度字段（理由见 `runtime.md` §1.3）。

判断始终由 Agent 结合当下证据临场做，不要写成「if 能解释 and 不爱动手 then …」这类半机械条件——
那会变成第二个 mastery engine。

**不做:** 调整只影响当前 session 的教学行为——不改 Graph（Graph 变更只走 PATCH，见 `protocols.md`）。

## 变体应用方式

```yaml
meta:
  pedagogy: programming  # 或 math-science / humanities / language / arts；无法判定时取 general
```
Runtime 主循环读取该字段,在对应环节应用变体规则；值未识别时的回退口径见 `runtime.md`「初始化」。
变体只影响 TEACH/PRACTICE/REINFORCE 的**内容形态**,不改流程结构——状态机、主循环环节、PATCH 全都一致。

**"无变体"的边界:** 标准流程指**不主动追加**学科特色内容。主题本身必须的例子(讲循环提一行伪代码)不算"暗地里走了 programming 变体"——变体是**主动选择增强手段**,不是"内容里出现像某学科的东西就算数"。
