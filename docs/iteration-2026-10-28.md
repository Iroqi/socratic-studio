# 第五十三轮：问句是界面——能力映射里不能有幽灵工具

> 日期：2026-10-28（用户本地）
> 基线：`2d3b089`（第 52 轮，读得出来的界面）
> 判决依据：一手博文（OpenAI GPT‑6 的 Intelligent UI）+ 工具面审计（prompt 适配层 / 运行时返回值 / README 活文档）+ 奥卡姆剃刀（零新增档 / 字段 / 状态，只改措辞与一条守卫测试）

## 一手依据：模型按"它真有什么"选形状

OpenAI 在 2026-10-07 的 GPT‑6 发布文里，把 Intelligent UI 描述成一套**原生可流式组件库 +
编译器**：模型不是自由画 HTML，而是在一组已知组件里选题、按场景拼装；界面质量按
"clarity, usefulness, and completeness" 评估。落到本仓，这套机制就是 `ui` 围栏的封闭词表
与 `web/ui-compile.js` 编译器。

机制要成立，有一个不写在博文里、但比措辞更硬的前提：**模型看到的"可用组件清单"必须
和宿主真能接住的清单是同一份**。清单里多一个不存在的东西，模型就会去调它；调了没人接，
这一回合就白烧——而学习者看到的是一张红卡，或一句永远等不到的提问。

## 审计：清单与宿主对不上的三处

第三十九轮把 `ask_user_question` 工具并进了 `question` 档，`buildTools()` 里已经没有它。
但"能力映射"是另一份清单，它按规则源语言逐条抄，抄漏了这次合并：

| 缺陷 | 现象 | 根因 |
|---|---|---|
| **能力映射表指向幽灵工具** | `server/prompt.mjs` 的映射行仍写"`ask_user_question` 工具 → …"，输出风格也写"就用 `ask_user_question`"。模型照着这张表去调，`validateToolCall` 直接以"未知工具"拒绝 | 第 39 轮改的是工具集，映射层按规则原文逐条转写，没有跟着工具集走 |
| **运行时最后一条指令也在指路** | `update_learning_graph` 成功返回的 `note` 仍写"调用 ask_user_question 收这次确认（`concept_id` 填 none，`allow_text` 保持开启）"。这是模型存完图后读到的**最后一句**，比 system prompt 更近 | 同上；且这条从未有过测试 |
| **README 活文档复述了幽灵** | 主循环图、能力映射表、mastery 那一行、"id 不再必填"那段，都按工具还存在来写 | 文档随第 39 轮之前的实现写成，之后没人回读 |

第三处不是代码，但它和代码犯的是同一个错：**描述当前能力的文字，不能比当前能力多一个入口**。
README 是这一仓的"第二份 prompt"——每个新回合的判断都从它开始。

## Brainstorm：候选表与判决

| 候选 | 价值 | 成本 / 风险 | 判决 |
|---|---|---|---|
| **修映射层 + 加守卫测试**（本轮）：prompt 映射行 / 输出风格 / 运行时 note / README 四处改成 `question` 档；新增"映射表点名的入口必须真实存在"测试 | 高：把"模型能调什么"与"宿主接得住什么"钉成同一份；同类漂移以后在 CI 就红 | 低：零新增语法 / 字段 / 状态；测试从 `buildTools()` 读真相，不维护第二份名单 | **做** |
| 把 `ask_user_question` 重新注册成工具（让两边一致） | 低：等于撤回第 39 轮的合并，收答会重新分叉成两条路 | 中：前端两套题卡、回放两套形状 | 不做 |
| 让 `question` 档在运行时拒绝"没有 conceptId"的收答 | 中：把 Seen 那条无条件边钉死在宿主 | 中：事务性提问合法地填 `none`，真正要防的是"漏填"，而围栏语法里它是可选字段；改成必填会让每一道当前合法的题卡在下一轮变成红卡 | 维持（提示词要求 + 本轮把它写清） |
| 用脚本从 `buildTools()` 生成映射表 | 中：理论上零漂移 | 高：映射表是"规则里的说法 ↔ 应用里的实现"的对照，左侧是自然语言，无法机械生成 | 不做 |
| README 全面回读（逐行核对工具名） | 中 | 中：本轮只修与幽灵工具直接相关的四处；全量回读留作独立候选 | 部分做 |

**为什么从 `buildTools()` 读真相**：测试如果维护一份"允许出现的工具名"白名单，它自己就会
成为第三份清单，下一次合并照样漏改。守卫测试直接取运行时注册表：

- 映射表 `## 工具映射` 段里每个反引号 token，要么是注册工具，要么是 `ui` 围栏；
- 问题控件那一行必须明说"工具集里没有这个工具"；
- 适配层里不许出现"调用 / 使用 `ask_user_question`"这类祈使句；
- 规则本体仍原样保留 `ask_user_question`（源语言不改写，改写的是适配层）。

## 方案

1. **映射行**：`| 平台原生问题控件 | **\`ui\` 围栏的 \`question\` 档**（原 \`ask_user_question\`
   工具已并入界面；**工具集里没有这个工具，别去找它**）…`，并写明"每次都要填 `conceptId`"。
2. **输出风格**："要停下来等学习者回答，就写一道 `ui` 围栏的 `question` 档——门禁确认也算。"
3. **运行时 note**："写一道 `ui` 围栏的 `question` 档收这次确认（`conceptId` 填 none；… `allowText`
   保持开启）"——字段名跟着围栏语法走（camelCase），不再混用旧工具入参的 snake_case。
4. **README**：主循环图、能力映射表、mastery 行、`id` 那段四处改为当前事实；
   历史叙述与 `docs/` 旧档案保持原样（它们是当时的记录）。
5. **导出 `APP_ADAPTER`**：测试需要读映射表本身，不再复制一份到测试里。
6. **零新增面**：不加档、不加字段、不加状态、不加 `data-*`、不改 `server/rules/`。
