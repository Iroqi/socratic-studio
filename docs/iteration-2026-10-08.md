# 迭代记录 — 2026-10-08（第十九轮）：落盘了，还得有人读回来

> 定时任务驱动的自由迭代（第十九轮）：pull 仓库 → 先跑测试摸实证现状 → 深度自由头脑风暴 →
> 设计迭代方案 → 实施 → 验证（四时区矩阵 + 每颗新钉子先红后绿的变异验证）→ 推送。
> 本轮四条改动都撞在同一个 bug 类上：**数据写进盘了，恢复它的那条路根本没实现**——
> 以及它的近亲「路由参数取了却不用」。三条落差全部由真服务探针撞出，不是读代码读出来的猜想。

## 1. 现状盘点（先跑，再撞）

- **基线（本沙箱 UTC，动手前实测）**：`npm run test:all` = **1763 项，6/6 全绿**（与第十八轮
  收口一致）。本轮新增 63 项断言，收口 **1826 项 / 6**。
- **探针一（`/tmp/p19/jobs-probe.mjs`，faux 真服务 + 同盘重启）——`jobs/*.json` 只写不读**：
  派一个真后台任务、等它 done → `GET /tasks` 回 1 条；杀掉服务、用**同一个 data 目录**再起一次 →
  `GET /tasks` 回 **0 条**，而盘上明明还躺着那一条 `done` 记录。`tasks.mjs:84` 的注释写着
  「建一条任务记录并落一个空文件，刷新/重启后还能翻出来」——`list` / `get` / `stop` 三个读口
  全部只遍历内存 `this.tasks`，全文件没有一行代码去 `readdir` 那个 `jobs/` 目录。
  这条注释的前半句（落盘）兑了，后半句（翻出来）从来没兑过。
- **探针二（`/tmp/p19/jobs-zombie.mjs`）——僵尸 `running` 永久残留**：
  让分身卡在 `ask_user_question` 上（没人答题，它永远 running），当场 SIGKILL 服务 →
  盘上那条记录**永远停在 `running`**。重启后 API 回 0 条（探针一的锅），所以谎暂时没人念；
  但只要按探针一的修法把记录读回来而不改判，界面与模型就会齐声管一条死了的任务叫「进行中」。
- **探针三（`/tmp/p19/cross-stop.mjs`）——stop 路由的 `:id` 是装饰品**：
  A、B 两本各挂一个后台任务。向 **A 本**的 URL 发
  `POST /api/notebooks/A/tasks/<B 的任务 id>/stop` → **200 `已请求停止 B 本的任务`**，
  B 的任务真的停了。路由把 `m[1]`（notebook id）解码出来赋给 `id`，然后**一次都没用它**。
  与第十八轮删除守卫同一类病：守卫只长在浏览器/URL 形状上，没长在动手那一侧。
- **前端这一侧（代码审读 + web-smoke 现状）**：`openNotebook()` 每次把 `state.tasks = []`，
  任务面板只靠常驻 SSE 的 `task_start` / `task_end` 实时事件填；`web/app.js` 全文
  **没有一处调用过 `GET /tasks`**（只有 stop 有调用点）。所以即便服务端有记录，
  刷新一次页面照样全空——探针一的前半句「刷新」也没兑。

## 2. 头脑风暴：候选方向一览

| # | 方向 | 价值 | 风险 | 工作量 | 结论 |
|---|---|---|---|---|---|
| 1 | **回读**：`list()` 扫 `jobs/*.json`，`get(id)` 内存查不到时按 id 找回盘上那份 | 高：兑那句「还能翻出来」；历史凭据不能只活在进程里 | 中：内存与盘两份账的优先级、串台防护 | M | ✅ 做（I1） |

| 4 | **补水**：前端 `openNotebook` 打一次 `GET /tasks`（不 await、失败静默、实时优先） | 高：面板不再"刷新即全空"；接口不再是没人调的孤儿 | 低：web-smoke fetch 桩会把未桩化 GET 打到真服务，须给默认桩 | S | ✅ 做（I4） |

| 9 | jobs 目录的保留策略 / 容量上限（跑几百轮后成百上千文件） | 中 | 中：删除要人拍板（处置台口径） | — | ⏸ 记进遗留 |
| 10 | 孤儿自动清理 / TTS / PDF / 鉴权 / 对话摘要压缩 | — | — | — | ⏸ 维持（历轮同案） |

**选定主题：「落盘了，还得有人读回来」** —— I1 兑现注释的下半句；I2 让读回来的状态如实；
I3 补上 stop 那道装饰性的门；I4 让前端真的去取；I5 让备份不再漏这段历史。
共同点：写侧都有、读侧都没有；URL 里有、代码里不用。第十八轮的元教训（守卫要站在动手那一侧）
本轮在 stop 上再次应验，说明这不是个案而是**默认习惯**：做功能时先做写、忘了做读。

## 3. 方案与实施

### 3.1 I1 — 回读（`server/tasks.mjs`）

- `_hydrate(notebookId)`：`readdirSync(jobsDir)` → 逐份 `readJsonSafe`（复用唯一读取口，
  第十八轮的纪律不动）→ 三条不认领：内存里已有该 id 的（内存优先，活任务的句柄与增量输出都
  在这里）、记录 `notebookId` 与这一本不符的（防串台，也防手改文件）、id 形状不对的。
- `list({notebookId})` 开口第一句 `this._hydrate(notebookId)`。没有 jobs 目录 = 没派过任务，
  `readdirSync` 抛错就地返回，正常状态。
- `get(id)` 内存查不到时走 `_findById(id)`：id 先过形状白名单 `/^(job|sub)-[0-9a-z]+-[0-9a-z]+$/`
  （畸形 id 根本不拿去拼路径），再按 `job-`↔`background`、`sub-`↔`subagent` 这对校验 kind——
  对不上就是被人动过的文件，不认领。

### 3.2 I2 — 如实（`server/tasks.mjs` + `agent.mjs` + `web/`）

- `statusFor(record)`：所有对外视图（list / get / 导出 / stop 的拒绝话术）唯一经过的状态换算。
  判据是「这台进程手里有没有它的句柄」（`live?.abort && live.status === 'running'`），
  不是盘上那个字段。为什么不按 createdAt 猜时间窗：`_create` 落盘与 `run()` 装上 abort 是
  紧挨着的两步，任何「刚写完盘就该算死」的猜测都会把这个窗口里的活任务误判成死的。
- 读回来发现 `running` → `interrupted` 且盘上还是 `running` 时，把 status/finishedAt/note
  **补写回文件一次**（只在重启后发生——活任务在 statusFor 那一步就是 running，碰不到这段；
  不动写盘热路径）。谎不许每刷新一次页面重圆一次。
- `stop()` 遇到 interrupted 直接说「没有还在跑的东西可停」，不再回那句含糊的「任务已经是 running」。
- `read_background_task` 读到 interrupted：`ok:false` + 原样转述 + 「要这个结果就重新派一次；
  别向学习者声称它已经完成」——模型拿到的就是把实话，圆不了场。
- 前端：`TASK_LABEL` 加 `interrupted: '已中断'`；中断卡片带一句 `t.note`（`.task-note`，
  服务端那句话一路带到面板）；CSS 徽章用 `--warning` 档（琥珀），卡片虚线边框——
  与「失败」（红）在视觉上分开：它不是做错了，是没做完就没了。

### 3.3 I3 — 归属（`server/serve.mjs` + `tasks.mjs` + `agent.mjs`）

`TaskRunner.stop(id, notebookId = null)` 本体先查 `r.notebookId !== notebookId`，
不匹配返回 `{ ok:false, crossNotebook:true, ... }`；路由只负责把它翻成 **404**
（这一本下面查无此任务）。`stop_background_task` 工具带 `this.notebook.id` 走同一道门。
默认参数 `null` 保留给确实不带上下文的内部调用，测试里逐条验证的是带上下文的真实路径。

### 3.4 I4 — 补水（`web/app.js`）

`openNotebook` 末尾 `hydrateTasks(id)`（不 await）：回来后若已切走别本，就地作废。
合并规则「实时优先」：本地已记成终态的任务，不用可能过期的快照降回 running——
快照发出后任务恰好跑完，是这个异步调用必然撞上的正常竞态。`.catch` 静默：
读不回来只是看不到历史任务，不许弄红「打开学习」。顶栏计数抽成 `updateTaskBadge()`，
SSE 与补水共用一个函数（两处各写一遍迟早各漂一遍）。

### 3.5 I5 — 导出带上 jobs（`server/store.mjs` + `serve.mjs`）

`exportNotebook` 新增 `jobs` 字段。store 不 import tasks.mjs（那会成环：tasks→agent→…），
由路由层 `store.setTasksSnapshotFn((id) => taskRunner.list({ notebookId: id }))` 注入——
顺带让导出的状态过了 `_hydrate` + `statusFor` 这道真实换算。未注入时兜一条读盘的路
（测试直接调 store 也拿得到）。`importNotebook` **有意无视** `bundle.jobs`，注释写明理由：
旧机器上的运行日志不属于新机器，照原样还原只会凭空造一堆永远等不到结论的「中断历史」。

### 3.6 文档（README）

新增「后台任务记录：落盘要有回读，状态要如实」一节（回读 / 如实 / 归属三件事 +
导出带 jobs、导入无视的名分）；目录树 `tasks.mjs` 行补「**回读**（第十九轮）」；
DSH 功能表「后台任务」行写明「SSE 推实时 + 打开时补水」；数据文件表 `jobs/` 行
记下「只写不读是本轮修掉的洞」。

### 4.4 实施与验证过程中翻出来的（原设计里没有）

1. **M7 的教训：形状钉子防不住"就地短路"。** `read_background_task` 那条契约钉认的是源码里
   `status: 'interrupted' … 重新派`这段形状还在不在——把 `if` 短路成 `if (false && …)`，
   文字原封不动，钉子在但行为已死（实测 contract 红 0）。这**不是**要再叠一条语义钉的理由，
   而是给变异验证定规矩：**对形状钉，变异必须"删掉整段"而不是"短路 if"**——短路只考行为钉，
   删除才考形状钉。M7/M7b 成对留下，就是这个口径的标本。
2. **`_findById` 第一版把 kind 映射写反了**（`job-` 前缀去找 `notebook-` 打头的 kind）：
   提交探针复跑前自查代码揪出来的——分身只跑了一次就改口不如先读一遍自己写的映射。
   前缀与 kind 是一对：`sub-`↔`subagent`、`job-`↔`background`。
3. **契约钉的正则差点又写成窗口泄漏**：`get(id)` 那条最初用 `{0,400}?_findById\(/` 的滑动窗口——
   M4 把 `_findById` 换成 `null` 后，窗口越过 `get()` 本体撞上**下一个方法**里的 `_findById` 定义，
   钉照样绿（红 0）。改成先把 `get(id) {…\n  }` 本体抓出来再在体内验——方法体钉的锚点必须是
   缩进两级那个真闭合，不能是"往后看 400 字符"。（与第十八轮 §4.1 同源：钉要钉语义边界，
   关键词和窗口都防不住搬家。）
4. **web-smoke 的 fetch 桩会把未桩化 GET 打到真服务**（`SOCCRATIC_BASE` 回退），补水一上线
   第 1 节起的所有 `openNotebook` 都会多打一发 `/tasks`。按预案给 nb-test 挂了默认空桩
   （`{ tasks: [] }`），第 35 节再换真桩逐条验；不这么做的后果是 700 多条断言集体时序漂移。
5. **`nextId` 被变异脚本手滑改坏过一次**（`-` 变空格再 `.replace` 圆回来）：当场看出不对，
   回滚。任务 id 的形状是 `_findById` 白名单正则的一部分，不能动。

## 5. 遗留（记在案）

1. **jobs 没有容量与保留策略**：每本一个 `jobs/`，跑几百轮就是成百上千个小文件；回读是
   整目录扫。该有个「只翻最近 N 条 / 归档旧记录」的口径——但删除归处置台管，等拍板。
2. **`interrupted` 的重派入口没做**：面板只会说"中断了"，不能一键「照原样再派一次」
   （instructions 可能含敏感原文，重派该有确认环节，不想顺手糊一个）。
3. **healthCheck 不看 `jobs/`**：本轮把僵尸治在读回时（补写），报告层不再需要重复点名；
   但如果没人打开过那本学习，僵尸就一直躺到有人翻它为止——是否要在体检里报「N 条中断记录」，
   等 §5.1 的容量口径一起定。
4. **`exportNotebook` 的 `jobs` 未加条数/字节上限**：uploads/artifacts 都有上限，jobs 暂时裸奔
   （单条 output 已有 20KB 截顶，量级可控）。跟 §5.1 一起收。
5. 第十八轮遗留照旧：证据副本的清理出口、`activeTurns` 死回合锁的回收、settings/credentials
   「正坏着」不进 `ok` 的口径。
